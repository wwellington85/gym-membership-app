# Complimentary access extensions

Admins can open Members → member record → Access passes → Extend access, choose a later expiration date, supply a reason and confirm a complimentary extension. The form previews the new end date and the existing 10 pm Jamaica cutoff. Front desk retains the existing renewal/purchase flow; security and members cannot extend passes.

The operation updates only the existing access pass's paid_through_date. Its start, facilities, discount snapshot, source, grant staff, payment link and original payment remain unchanged. No payment, refund, renewal or visit is created. Paid and complimentary passes use the same extension action. An ended pass can be restored to a valid future expiry; revoked passes and inactive members are blocked. Upcoming passes retain their original start date.

Apply 20261114160000_complimentary_access_extensions.sql before the application deployment. It adds service-only extension history and the admin-authorized extend_access_pass RPC, without altering any existing pass. The RPC locks the member and pass, checks the submitted previous expiry to prevent stale forms from overwriting a newer extension, and accepts an idempotency key so repeated submissions do not duplicate history. Invalid/past/shortened expiries are rejected, including today's date after 10 pm Jamaica time. History and date changes are transactional: an audit/history failure rolls everything back.

Each history row stores the prior and new dates, staff actor, reason, timestamp and submission key. An explicit access_pass_extended programme audit event records those details and marks the extension complimentary. Existing generic access-pass change audit events remain in place. The member record displays extension history; the member's Access page labels passes with complimentary extensions without exposing internal staff reasons. Home, Card, verification, discounts and renewal calculations already read the authoritative pass expiry.
